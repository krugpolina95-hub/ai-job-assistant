1. ОБЩАЯ ИНФОРМАЦИЯ
======================================================================

1.1. Наименование
AI Job Assistant — веб-сервис для интеллектуального поиска вакансий.

1.2. Цель
Создать международный веб-сервис, который позволяет пользователю:
- зарегистрироваться и создать персональный профиль;
- описать желаемую работу обычным языком;
- получить уточняющие вопросы от AI;
- автоматически использовать приблизительное местоположение;
- найти вакансии из доступных внешних источников;
- отфильтровать и структурировать найденные вакансии;
- оценить соответствие вакансий профилю пользователя;
- сохранить интересующие вакансии;
- сравнить несколько вакансий.

1.3. Границы MVP
В MVP входят:
- регистрация, вход и личный кабинет;
- профиль пользователя;
- AI-помощь при формировании поискового запроса;
- поиск вакансий через разрешённые источники;
- фильтрация и нормализация вакансий;
- приблизительное определение местоположения;
- сохранение вакансий;
- сравнение вакансий;
- история поисковых запросов.

В MVP НЕ входят:
- автоматическая отправка откликов;
- автоматический мониторинг электронной почты;
- автоматические ответы работодателям;
- полноценный конструктор резюме;
- платёжная система;
- мобильное приложение;
- сложная рекомендательная ML-модель;
- обход CAPTCHA, авторизации и технических ограничений сайтов.

1.4. Целевая аудитория
Международные пользователи, включая:
- студентов;
- стажёров;
- junior-специалистов;
- специалистов с опытом;
- пользователей, ищущих удалённую работу;
- пользователей, желающих сменить профессию.

1.5. Языки
MVP:
- английский;
- русский.

Архитектура должна позволять добавить другие языки без переработки всей системы.

3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
======================================================================

3.1. AUTH — регистрация и авторизация

AUTH-001
Пользователь должен иметь возможность зарегистрироваться по email и паролю.

AUTH-002
Система должна проверять:
- корректность email;
- минимальную длину пароля;
- уникальность email;
- подтверждение согласия с политикой конфиденциальности и условиями использования.

AUTH-003
Пароли должны храниться только в виде безопасного хеша Argon2id или bcrypt.

AUTH-004
Пользователь должен иметь возможность:
- войти;
- выйти;
- получить информацию о текущем пользователе;
- изменить пароль;
- запросить восстановление пароля.

AUTH-005
API должен предотвращать доступ одного пользователя к данным другого пользователя.

AUTH-006
Должны быть предусмотрены:
- ограничение частоты запросов;
- безопасные cookie или короткоживущие access tokens;
- защита от перебора паролей;
- журналирование подозрительных попыток входа.

Критерии приёмки:
- регистрация с уже существующим email отклоняется;
- неверный пароль не раскрывает лишнюю информацию;
- защищённые endpoints недоступны без авторизации;
- пользователь не может изменить чужие записи.


3.2. PROFILE — профиль пользователя

PROFILE-001
Пользователь может указать:
- имя;
- страну;
- город или регион;
- желаемые должности;
- минимальную и максимальную зарплату;
- валюту;
- формат работы;
- тип занятости;
- уровень опыта;
- навыки;
- языки;
- готовность к переезду.

PROFILE-002
Пользователь может редактировать профиль в любое время.

PROFILE-003
Профиль должен использоваться при AI-анализе вакансий только в пределах разрешённых пользователем данных.

PROFILE-004
Пользователь должен видеть, какие данные используются для персонализации.

Критерии приёмки:
- данные профиля сохраняются в БД;
- изменения отражаются в следующем поиске;
- обязательные поля валидируются;
- пользователь может удалить или изменить свои данные.


3.3. SEARCH — создание поискового запроса

SEARCH-001
Пользователь может создать запрос через:
- обычную форму;
- AI-чат.

SEARCH-002
Параметры поиска:
- должность;
- ключевые слова;
- минимальная зарплата;
- максимальная зарплата;
- валюта;
- страна;
- город;
- радиус;
- формат работы;
- уровень опыта;
- тип занятости;
- навыки;
- язык вакансии;
- дата публикации;
- готовность к переезду.

SEARCH-003
Должность является обязательным параметром.

SEARCH-004
Система должна показывать итоговые параметры перед запуском поиска.

SEARCH-005
Пользователь должен иметь возможность изменить параметры перед подтверждением.

SEARCH-006
Длительный поиск должен выполняться асинхронно. API возвращает job_id, а интерфейс отображает статус:
- pending;
- running;
- completed;
- partially_completed;
- failed;
- cancelled.

Критерии приёмки:
- пустая должность отклоняется;
- некорректные значения зарплаты отклоняются;
- пользователь видит подтверждение параметров;
- повторный запрос не создаёт неконтролируемое количество задач.


3.4. AI-CHAT — AI-помощник

AI-001
AI должен преобразовывать естественный язык пользователя в структурированный JSON.

AI-002
AI должен задавать уточняющие вопросы только по действительно отсутствующим или неоднозначным параметрам.

AI-003
AI должен учитывать:
- профиль пользователя;
- предыдущие поисковые запросы, если пользователь разрешил такое использование;
- текущие параметры поиска;
- выбранную локаль и язык.

AI-004
AI не должен выдумывать:
- навыки;
- опыт;
- зарплату;
- работодателей;
- наличие вакансии;
- требования вакансии.

AI-005
AI должен возвращать:
- нормализованные параметры;
- список уточняющих вопросов;
- предупреждения о недостатке данных;
- краткое объяснение преобразований.

Пример JSON:
{
  "roles": ["Python Developer", "QA Automation Engineer"],
  "salary_min": 800,
  "salary_max": null,
  "currency": "EUR",
  "location": {
    "country": "Lithuania",
    "city": "Vilnius",
    "source": "ip_estimate"
  },
  "work_formats": ["remote", "hybrid"],
  "experience_level": ["intern", "junior"],
  "skills": ["Python", "Selenium"],
  "employment_types": ["internship", "full_time"],
  "missing_information": ["preferred_language"],
  "needs_confirmation": true
}

AI-006
AI должен работать через backend или защищённые credentials n8n. API-ключи не должны попадать в браузер.

AI-007
Все ответы AI должны проходить серверную валидацию по схеме Pydantic/Zod.

AI-008
AI-оценка вакансии является ориентировочной рекомендацией, а не гарантией трудоустройства.


3.5. LOCATION — местоположение

LOCATION-001
Система должна пытаться определить приблизительный регион пользователя без обязательного вопроса в AI-диалоге.

Приоритет:
1. Явно сохранённое пользователем местоположение.
2. Приблизительная IP-геолокация.
3. Ручной ввод пользователя.

LOCATION-002
Система должна отображать определённое местоположение и давать возможность его изменить.

LOCATION-003
Точная геолокация браузера может использоваться только после явного разрешения пользователя.

LOCATION-004
Точные координаты не должны сохраняться, если для поиска достаточно города или региона.

LOCATION-005
Нужно учитывать ошибки:
- VPN;
- прокси;
- мобильная сеть;
- неточная база IP;
- отсутствие разрешения браузера.

Пример сообщения:
«Определён приблизительный регион: Vilnius, Lithuania. Вы можете изменить его перед поиском.»


3.6. SOURCES — внешние источники

Потенциальные источники:
- официальные API;
- разрешённые RSS-ленты;
- поисковые системы;
- LinkedIn;
- Indeed;
- белорусские сайты вакансий;
- другие сайты с разрешённым доступом.

ВАЖНО:
Подключение LinkedIn, Indeed и других источников возможно только в рамках их актуальных условий, документации, ограничений и доступных разрешений. Нельзя считать, что любой сайт предоставляет свободный API для массового поиска.

Для MVP рекомендуется:
- сначала подключить 1–3 источника с понятным API или разрешённым доступом;
- для остальных реализовать архитектурные адаптеры без включения недопустимого scraping;
- всегда сохранять ссылку на оригинальный источник.

SOURCE-001
Каждый источник должен иметь отдельный адаптер:
- search();
- normalize();
- validate();
- get_source_name();
- get_rate_limits().

SOURCE-002
Система должна обрабатывать:
- отсутствие зарплаты;
- отсутствие даты публикации;
- разные валюты;
- дубликаты;
- удалённые вакансии;
- неполное описание;
- временную недоступность источника.

SOURCE-003
Нельзя:
- обходить CAPTCHA;
- обходить ограничения доступа;
- скрывать идентичность приложения;
- нарушать условия сайта;
- хранить больше данных, чем необходимо;
- копировать полные тексты объявлений без правового основания.

SOURCE-004
В интерфейсе отображается:
- название источника;
- ссылка на оригинал;
- дата получения данных;
- предупреждение об актуальности.


3.7. VACANCIES — нормализация вакансий

Для каждой вакансии сохраняются:
- title;
- company;
- description;
- responsibilities;
- requirements;
- salary_min;
- salary_max;
- salary_currency;
- country;
- city;
- remote_type;
- employment_type;
- experience_level;
- skills;
- source;
- external_id;
- url;
- published_at;
- collected_at;
- last_verified_at;
- content_hash.

VACANCY-001
Дубликаты определяются по:
- source + external_id;
- canonical URL;
- content_hash;
- комбинации названия, компании и локации при отсутствии ID.

VACANCY-002
Система должна сохранять оригинальный URL и не подменять его внутренней ссылкой без необходимости.

VACANCY-003
Если зарплата отсутствует, интерфейс показывает «Не указана», а не предполагаемое значение.

VACANCY-004
Если вакансия устарела или источник недоступен, это должно быть обозначено.


3.8. MATCHING — сопоставление вакансий

MATCH-001
Система должна сравнивать вакансию с профилем и параметрами поиска.

Факторы:
- совпадение должности;
- навыки;
- уровень опыта;
- зарплата;
- локация;
- формат работы;
- тип занятости;
- язык;
- свежесть вакансии.

MATCH-002
Результат должен содержать:
- уровень соответствия;
- совпадающие навыки;
- отсутствующие навыки;
- причины рекомендации;
- ограничения и предупреждения.

MATCH-003
Не следует показывать процент как объективную вероятность получения работы. В MVP рекомендуется использовать:
- High match;
- Medium match;
- Low match;
с объяснением факторов.

MATCH-004
Ранжирование не должно использовать чувствительные персональные данные, не относящиеся к профессиональному соответствию.

MATCH-005
Пользователь должен иметь возможность сортировать результаты самостоятельно.


3.9. SAVED — сохранение вакансий

SAVED-001
Авторизованный пользователь может сохранить вакансию.

SAVED-002
Пользователь может:
- удалить вакансию из сохранённых;
- добавить заметку;
- открыть оригинальную ссылку;
- просмотреть дату сохранения.

SAVED-003
Одна вакансия не должна сохраняться повторно в одной коллекции пользователя.

SAVED-004
Сохранённые вакансии должны быть доступны только владельцу.


3.10. COMPARE — сравнение вакансий

COMPARE-001
Пользователь может выбрать от 2 до 5 вакансий.

COMPARE-002
Сравнение отображает:
- должность;
- компанию;
- зарплату;
- локацию;
- формат;
- тип занятости;
- опыт;
- ключевые навыки;
- совпадение с профилем;
- ссылку на источник.

COMPARE-003
Если данные отсутствуют, показывается «Нет данных».

COMPARE-004
Сравнение не должно автоматически объявлять одну вакансию лучшей без объяснения критериев. Пользователь должен видеть различия и самостоятельно принимать решение.

4. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
======================================================================

4.1. Производительность
- обычные API-запросы должны отвечать в разумный срок;
- поиск выполняется в фоне;
- интерфейс показывает прогресс;
- внешние запросы имеют timeout;
- количество параллельных запросов ограничивается.

4.2. Надёжность
- ошибки одного источника не должны ломать весь поиск;
- workflow можно безопасно повторить;
- повторный запуск не должен создавать дубликаты;
- важные операции логируются.

4.3. Масштабируемость
- источники подключаются через адаптеры;
- AI-провайдер может быть заменён;
- frontend и backend развёртываются независимо;
- n8n не должен быть единственным местом хранения бизнес-данных.

4.4. Доступность
- управление с клавиатуры;
- понятные labels;
- достаточный контраст;
- сообщения об ошибках рядом с полями;
- адаптация для мобильных экранов.

4.5. Локализация
- все пользовательские тексты хранятся отдельно от логики;
- даты, числа и валюты форматируются по локали;
- часовой пояс хранится и отображается корректно.

5. АРХИТЕКТУРА

5.1. Компоненты

Frontend:
- Next.js;
- React;
- TypeScript;
- Tailwind CSS;
- shadcn/ui;
- React Hook Form;
- Zod;
- TanStack Query.

Backend:
- FastAPI;
- Python;
- Pydantic;
- SQLAlchemy;
- Alembic;
- PostgreSQL.

Automation:
- n8n;
- Webhook;
- Cron;
- AI node или HTTP Request;
- обработка ошибок;
- уведомления в будущем.

Инфраструктура:
- Docker Compose для локальной разработки;
- reverse proxy;
- HTTPS;
- CI/CD в будущем;
- централизованное логирование.

5.2. Поток поиска

1. Пользователь вводит запрос.
2. Frontend отправляет запрос в FastAPI.
3. FastAPI проверяет авторизацию и данные.
4. Backend получает профиль пользователя.
5. Backend вызывает n8n webhook.
6. n8n нормализует параметры и вызывает доступные источники.
7. n8n удаляет дубликаты и нормализует результаты.
8. Вакансии сохраняются в PostgreSQL через защищённый backend endpoint или внутренний механизм.
9. AI-модуль формирует объяснения соответствия.
10. Frontend получает job_id и запрашивает статус.
11. После завершения отображаются результаты.

8. n8n WORKFLOWS
======================================================================

8.1. WF-001 — Search Request

Nodes:
1. Webhook.
2. Validate signature.
3. Validate payload.
4. Get profile from backend.
5. Merge search parameters.
6. Normalize query.
7. Save job status = running.
8. Execute source search workflows.
9. Merge results.
10. Deduplicate.
11. Normalize vacancies.
12. Save vacancies.
13. Calculate matching data.
14. Update job status = completed.
15. Error Trigger / error handler.

8.2. WF-002 — Source Search

Для каждого источника:
1. Получить параметры.
2. Проверить rate limit.
3. Отправить запрос разрешённым способом.
4. Проверить HTTP-ответ.
5. Преобразовать ответ в общий формат.
6. Записать ошибку источника, если он недоступен.
7. Вернуть нормализованный массив вакансий.

8.3. WF-003 — AI Clarification

1. Получить исходный текст.
2. Получить разрешённые данные профиля.
3. Передать данные AI.
4. Получить JSON.
5. Проверить JSON по схеме.
6. Вернуть уточняющие вопросы или итоговые параметры.
7. Сохранить только необходимую информацию.

8.4. WF-004 — Matching

1. Получить вакансию.
2. Получить параметры поиска.
3. Получить профессиональные данные пользователя.
4. Рассчитать структурированные признаки.
5. Запросить AI-объяснение при необходимости.
6. Проверить ответ.
7. Сохранить match.
8. Вернуть объяснение frontend.

8.5. Идемпотентность
Каждый workflow должен поддерживать:
- request_id;
- job_id;
- повторный запуск;
- защиту от дубликатов;
- контроль таймаутов;
- обработку частичного результата.

8.6. Секреты
- credentials n8n не должны храниться в Git;
- API-ключи в переменных окружения или секрет-хранилище;
- webhook защищается подписью или сервисным токеном;
- доступ n8n к backend ограничивается.

15. РИСКИ И МЕРЫ СНИЖЕНИЯ
======================================================================

Риск: отсутствие доступа к API LinkedIn или Indeed.
Мера: использовать официальные программы доступа или альтернативные разрешённые источники; не строить MVP на неподтверждённом доступе.

Риск: устаревшие вакансии.
Мера: хранить collected_at и last_verified_at; показывать предупреждения.

Риск: AI выдумывает данные.
Мера: строгие схемы, проверка источника, запрет на генерацию фактов, отображение оригинальной ссылки.

Риск: большие расходы на AI.
Мера: ограничение длины текста, кэширование, лимиты, выбор модели по типу задачи, логирование токенов.

Риск: утечка персональных данных.
Мера: минимизация данных, контроль доступа, шифрование каналов, безопасное хранение секретов.

Риск: дублирование вакансий.
Мера: external_id, canonical URL, content_hash и дедупликация.

Риск: n8n становится единственной бизнес-логикой.
Мера: важные правила и доступ к данным держать в FastAPI; n8n использовать для оркестрации.

Риск: слишком большой объём MVP.
Мера: ограничить первые источники и реализовать только поиск, профиль, AI, сохранение и сравнение.

18. ИТОГ
======================================================================

AI Job Assistant должен быть построен как модульная система:

Frontend:
отвечает за интерфейс, формы, результаты и пользовательские действия.

FastAPI:
отвечает за авторизацию, бизнес-логику, валидацию, доступ к БД и защиту данных.

PostgreSQL:
отвечает за хранение пользователей, профилей, поисков, вакансий и сохранённых результатов.

n8n:
отвечает за оркестрацию поиска, внешние интеграции, AI-workflow и обработку фоновых задач.

AI:
отвечает за обработку естественного языка, уточнение параметров и объяснение соответствия, но не должен выдумывать факты и выполнять необратимые действия без подтверждения.

Рекомендуемый принцип разработки:
Сначала реализовать небольшой стабильный вертикальный сценарий:

Регистрация
-> Профиль
-> Поисковый запрос
-> AI-уточнение
-> n8n
-> Один разрешённый источник
-> Нормализация
-> Результаты
-> Сохранение
-> Сравнение

После успешной проверки этого сценария подключать дополнительные источники и функции.
