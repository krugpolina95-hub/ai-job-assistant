# API Reference

The OpenAPI document generated by FastAPI is authoritative. In `local`/`test` it is served at `/api/v1/openapi.json`, with Swagger UI at `/api/v1/docs`. This page covers the conventions, authentication and the error catalog. Endpoints are added here as features ship.

## Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1`. The browser reaches it only through the Next.js rewrite (TD-05). |
| Format | JSON, UTF-8, `snake_case` fields, ISO-8601 UTC timestamps, UUID identifiers. |
| Request bodies | At most **64 KB** (`MAX_REQUEST_BODY_BYTES`). Unknown fields are rejected (`InputSchema`, `extra="forbid"`). Strings are trimmed, except passwords. |
| Request ID | Every response carries `X-Request-ID`. A well-formed incoming `X-Request-ID` (`[A-Za-z0-9._-]{1,128}`) is reused, so logs correlate across frontend, backend and n8n (TD-21). Anything else is replaced with a new ID. |
| Security headers | Every response: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. |
| Authentication | Cookie session (see [Authentication](#authentication)). Every route except health, register and login requires it. |
| Cross-user access | A resource owned by another user returns **404 `NOT_FOUND`**, never 403 (TD-19). |
| Pagination | Cursor based: `?cursor=&limit=` → `{items, next_cursor}`, maximum limit 100 (added with the first list endpoint). |

## Authentication

Opaque server-side sessions in cookies (TD-03). No token is ever readable by JavaScript or stored in `localStorage`.

| Cookie | Attributes | Purpose |
|---|---|---|
| `sid` | `HttpOnly; Secure; SameSite=Lax; Path=/` | Random 256-bit session token. The server stores only its SHA-256. Without "remember me" it is a browser-session cookie (server-side limit 12 h); with it, `Max-Age` is 30 days. The session also ends after 7 days of inactivity. |
| `csrf` | `Secure; SameSite=Lax; Path=/` (readable by JS) | Double-submit CSRF token. |

- **CSRF:** every `POST`/`PUT`/`PATCH`/`DELETE` on a protected route must send the `csrf` cookie value in the `X-CSRF-Token` header, otherwise `403 CSRF_FAILED`. Authentication is checked first, so a request without a session gets `401`. Register and login take no session; they only accept JSON bodies, so a cross-site HTML form can't submit them.
- **Token rotation:** every login issues a new token and deletes the session the browser had before (session fixation).
- **Frontend flow:** call `GET /auth/me` to learn whether the user is signed in (401 means no). It also re-issues a missing `csrf` cookie.

## Error envelope

Every error response, including 404 for unknown routes, 405, 413 and unexpected 500s, has this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [{"loc": ["body", "salary_max"], "type": "greater_than_equal", "message": "Input should be greater than or equal to 0"}],
    "request_id": "01a0e4b317b6717aa6a4ddd76ce8f209"
  }
}
```

- `code` is stable and machine-readable. The frontend translates it into the user's language (TD-20).
- `message` is English developer text. Don't show it to users as-is.
- `details` is optional and depends on the code. For request validation it is a list of `{loc, type, message}`. The rejected input value is **never echoed back**, since it could be a password.
- `request_id` matches the `X-Request-ID` header and the backend logs.

## Error catalog

Defined in `backend/app/core/errors.py`. New codes are added with the feature that raises them (for example `RATE_LIMITED` with rate limiting, `JOB_LIMIT_REACHED` in M5, `AI_UNAVAILABLE` in M7).

| Code | HTTP | Raised when |
|---|---|---|
| `BAD_REQUEST` | 400 | Malformed request the framework can't interpret, e.g. an invalid `Content-Length`. |
| `VALIDATION_ERROR` | 422 | The request body, query or path fails schema validation, or a service rejects input with `ValidationFailedError`. |
| `UNAUTHENTICATED` | 401 | No valid session: cookie missing, unknown, expired or logged out. The reason is not disclosed. |
| `INVALID_CREDENTIALS` | 401 | Login failed. Identical for an unknown email and a wrong password. |
| `CSRF_FAILED` | 403 | Unsafe request on a session without a matching `X-CSRF-Token` header. |
| `NOT_FOUND` | 404 | Unknown route, missing resource, or a resource owned by another user (`NotFoundError`). |
| `METHOD_NOT_ALLOWED` | 405 | The route exists but not for this method. The `Allow` header lists valid methods. |
| `CONFLICT` | 409 | The request conflicts with the current state (`ConflictError`). |
| `EMAIL_ALREADY_REGISTERED` | 409 | Registration with an email that already has an account (case-insensitive). |
| `PAYLOAD_TOO_LARGE` | 413 | The body exceeds 64 KB (declared `Content-Length` or streamed). |
| `INTERNAL_ERROR` | 500 | Any unexpected exception. The message is always generic, and details are only in the logs under the same `request_id`. |

## Endpoints

### Health

| Method | Path | Response |
|---|---|---|
| GET | `/api/v1/health` | `200 {"status": "ok"}`. Liveness: the process is up. No dependencies are checked. |
| GET | `/api/v1/ready` | `200 {"status": "ok", "checks": {"database": "ok", "redis": "ok"}}`, or **503** with the same shape and `"unavailable"` for each failing check. Each check times out after `READINESS_TIMEOUT_SECONDS`. |

`/ready` reports dependency state rather than an error, so its 503 body uses the readiness shape instead of the error envelope. Load balancers and Compose health checks rely on it.

### Auth

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| POST | `/api/v1/auth/register` | none | `{email, password, accept_terms: true, preferred_locale?: "en" or "ru", timezone?: IANA name}` | `201 UserOut`; sets `sid` + `csrf`, so the user is signed in (browser-session cookie). |
| POST | `/api/v1/auth/login` | none | `{email, password, remember_me?: false}` | `200 UserOut`; sets a new `sid` + `csrf`. |
| POST | `/api/v1/auth/logout` | session + CSRF | none | `204`; deletes this session only and clears both cookies. |
| GET | `/api/v1/auth/me` | session | none | `200 UserOut`. |

`UserOut`: `{id, email, is_verified, preferred_locale, timezone, created_at}`. It never contains the password hash, session data or admin flags.

Validation (`422 VALIDATION_ERROR`): email must be valid and ≤ 254 characters; password 10–128 characters (used exactly as typed, including spaces) and not equal to the email; `accept_terms` must be `true`, and the accepted terms/privacy versions are stored with the account; unknown fields are rejected.

Errors: register → `409 EMAIL_ALREADY_REGISTERED`; login → `401 INVALID_CREDENTIALS`; protected routes → `401 UNAUTHENTICATED`, and unsafe ones also `403 CSRF_FAILED`.
