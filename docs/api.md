# API Reference

The OpenAPI document generated by FastAPI is authoritative. In `local`/`test` it is served at `/api/v1/openapi.json`, with Swagger UI at `/api/v1/docs`. This page covers the conventions, authentication and the error catalog. Endpoints are added here as features ship.

## Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1`. The browser reaches it only through the Next.js rewrite (TD-05). |
| Format | JSON, UTF-8, `snake_case` fields, ISO-8601 UTC timestamps, UUID identifiers. |
| Request bodies | At most **64 KB** (`MAX_REQUEST_BODY_BYTES`). Unknown fields are rejected (`InputSchema`, `extra="forbid"`). Strings are trimmed, except passwords. |
| Request ID | Every response carries `X-Request-ID`. A well-formed incoming `X-Request-ID` (`[A-Za-z0-9._-]{1,128}`) is reused, so logs correlate across frontend, backend and n8n (TD-21). Anything else is replaced with a new ID. |
| Security headers | Every response: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. |
| Authentication | Cookie session (see [Authentication](#authentication)). Every route except health, register and login requires it. |
| Cross-user access | A resource owned by another user returns **404 `NOT_FOUND`**, never 403 (TD-19). |
| Pagination | Cursor based: `?cursor=&limit=` → `{items, next_cursor}`, maximum limit 100 (added with the first list endpoint). |

## Authentication

Opaque server-side sessions in cookies (TD-03). No token is ever readable by JavaScript or stored in `localStorage`.

| Cookie | Attributes | Purpose |
|---|---|---|
| `sid` | `HttpOnly; Secure; SameSite=Lax; Path=/` | Random 256-bit session token. The server stores only its SHA-256. Without "remember me" it is a browser-session cookie (server-side limit 12 h); with it, `Max-Age` is 30 days. The session also ends after 7 days of inactivity. |
| `csrf` | `Secure; SameSite=Lax; Path=/` (readable by JS) | Double-submit CSRF token. |

- **CSRF:** every `POST`/`PUT`/`PATCH`/`DELETE` on a protected route must send the `csrf` cookie value in the `X-CSRF-Token` header, otherwise `403 CSRF_FAILED`. Authentication is checked first, so a request without a session gets `401`. Register and login take no session; they only accept JSON bodies, so a cross-site HTML form can't submit them.
- **Token rotation:** every login issues a new token and deletes the session the browser had before (session fixation). A password change replaces every session of the user, this browser's included, with one new session; a password reset deletes them all.
- **Frontend flow:** call `GET /auth/me` to learn whether the user is signed in (401 means no). It also re-issues a missing `csrf` cookie.

## Error envelope

Every error response, including 404 for unknown routes, 405, 413 and unexpected 500s, has this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [{"loc": ["body", "salary_max"], "type": "greater_than_equal", "message": "Input should be greater than or equal to 0"}],
    "request_id": "01a0e4b317b6717aa6a4ddd76ce8f209"
  }
}
```

- `code` is stable and machine-readable. The frontend translates it into the user's language (TD-20).
- `message` is English developer text. Don't show it to users as-is.
- `details` is optional and depends on the code. For request validation it is a list of `{loc, type, message}`. The rejected input value is **never echoed back**, since it could be a password.
- `request_id` matches the `X-Request-ID` header and the backend logs.

## Error catalog

Defined in `backend/app/core/errors.py`. New codes are added with the feature that raises them (for example `RATE_LIMITED` with rate limiting, `JOB_LIMIT_REACHED` in M5, `AI_UNAVAILABLE` in M7).

| Code | HTTP | Raised when |
|---|---|---|
| `BAD_REQUEST` | 400 | Malformed request the framework can't interpret, e.g. an invalid `Content-Length`. |
| `VALIDATION_ERROR` | 422 | The request body, query or path fails schema validation, or a service rejects input with `ValidationFailedError`. |
| `UNAUTHENTICATED` | 401 | No valid session: cookie missing, unknown, expired or logged out. The reason is not disclosed. |
| `INVALID_CREDENTIALS` | 401 | Login failed. Identical for an unknown email, a wrong password and a locked account. |
| `INVALID_CURRENT_PASSWORD` | 400 | Password change with a wrong current password (the session stays valid, so not 401). |
| `RESET_TOKEN_INVALID` | 400 | Password reset with an unknown, expired or already used link. The three cases are not distinguished. |
| `CSRF_FAILED` | 403 | Unsafe request on a session without a matching `X-CSRF-Token` header. |
| `NOT_FOUND` | 404 | Unknown route, missing resource, or a resource owned by another user (`NotFoundError`). |
| `METHOD_NOT_ALLOWED` | 405 | The route exists but not for this method. The `Allow` header lists valid methods. |
| `CONFLICT` | 409 | The request conflicts with the current state (`ConflictError`). |
| `EMAIL_ALREADY_REGISTERED` | 409 | Registration with an email that already has an account (case-insensitive). |
| `SOURCE_NOT_ENABLED` | 409 | Ingestion for a source that is unknown, disabled or not compliance-reviewed. Internal ingestion only; not returned by public endpoints. |
| `SEARCH_NOT_CONFIRMED` | 409 | Running a search whose parameters aren't confirmed. |
| `NO_SOURCES_ENABLED` | 409 | Running a search while no job source is enabled. |
| `JOB_LIMIT_REACHED` | 409 | The user already has the maximum number of active runs. |
| `IDEMPOTENCY_KEY_REUSED` | 409 | An `Idempotency-Key` already used for a different search. |
| `JOB_ALREADY_FINISHED` | 409 | Cancelling a run that already completed or failed. |
| `JOB_NOT_RUNNING` | 410 | Internal API only: the run was cancelled or already finished, so n8n should stop working on it. |
| `RATE_LIMITED` | 429 | A request limit was hit: too many search runs in the last hour, too many auth attempts (see [Auth](#auth)), or the AI quota (`ai_calls_per_day`: 50 per rolling 24 h, `ai_calls_per_minute`: 10). `details.limit` names the limit. Auth and per-minute AI limits also send `Retry-After` (seconds). |
| `AI_UNAVAILABLE` | 503 | The AI assistant can't answer: no provider configured, provider down or rate-limited, timed out, or paused after repeated failures. The UI falls back to the search form (architecture §9). No AI endpoint exists yet (M7.5). |
| `AI_INVALID_RESPONSE` | 502 | The AI answered twice without matching the expected structure (AI-007). The UI falls back to the form. |
| `PAYLOAD_TOO_LARGE` | 413 | The body exceeds 64 KB (declared `Content-Length` or streamed). |
| `INTERNAL_ERROR` | 500 | Any unexpected exception. The message is always generic, and details are only in the logs under the same `request_id`. |

## Endpoints

### Health

| Method | Path | Response |
|---|---|---|
| GET | `/api/v1/health` | `200 {"status": "ok"}`. Liveness: the process is up. No dependencies are checked. |
| GET | `/api/v1/ready` | `200 {"status": "ok", "checks": {"database": "ok", "redis": "ok"}}`, or **503** with the same shape and `"unavailable"` for each failing check. Each check times out after `READINESS_TIMEOUT_SECONDS`. |

`/ready` reports dependency state rather than an error, so its 503 body uses the readiness shape instead of the error envelope. Load balancers and Compose health checks rely on it.

### Auth

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| POST | `/api/v1/auth/register` | none | `{email, password, accept_terms: true, preferred_locale?: "en" or "ru", timezone?: IANA name}` | `201 UserOut`; sets `sid` + `csrf`, so the user is signed in (browser-session cookie). |
| POST | `/api/v1/auth/login` | none | `{email, password, remember_me?: false}` | `200 UserOut`; sets a new `sid` + `csrf`. |
| POST | `/api/v1/auth/logout` | session + CSRF | none | `204`; deletes this session only and clears both cookies. |
| GET | `/api/v1/auth/me` | session | none | `200 UserOut`. |
| POST | `/api/v1/auth/change-password` | session + CSRF | `{current_password, new_password}` | `204`; sets a new `sid` + `csrf` (same persistence as before). Every other session of the user ends. |
| POST | `/api/v1/auth/forgot-password` | none | `{email}` | `202`, empty body, **always**: whether or not the email has an account. If it has, a reset link valid for 30 minutes is emailed in the account's language. |
| POST | `/api/v1/auth/reset-password` | none | `{token, new_password}` | `204`; sets the password, ends every session (cookies cleared) and lifts a login lockout. The user then logs in. |

`UserOut`: `{id, email, is_verified, preferred_locale, timezone, created_at}`. It never contains the password hash, session data or admin flags.

Validation (`422 VALIDATION_ERROR`): email must be valid and ≤ 254 characters; password 10–128 characters (used exactly as typed, including spaces) and not equal to the email; `accept_terms` must be `true`, and the accepted terms/privacy versions are stored with the account; unknown fields are rejected.

Validation of the new endpoints: `new_password` follows the registration rules (10–128 characters, not the account's email); `token` is the value from the link (URL-safe characters, 20–128).

Errors: register → `409 EMAIL_ALREADY_REGISTERED`; login → `401 INVALID_CREDENTIALS`; change-password → `400 INVALID_CURRENT_PASSWORD`; reset-password → `400 RESET_TOKEN_INVALID`; protected routes → `401 UNAUTHENTICATED`, and unsafe ones also `403 CSRF_FAILED`; any auth route → `429 RATE_LIMITED`.

**Reset link.** `{APP_PUBLIC_URL}/{locale}/reset-password#token=<token>`. The token is in the URL fragment, which browsers never send to a server or in `Referer`; the reset page reads it and posts it to `/auth/reset-password`. Only the newest link of an account works, and only once.

**Brute-force protection (AUTH-006).** Limits per client IP (behind the proxies, see `TRUSTED_PROXY_COUNT`), email or user, over a sliding window:

| `details.limit` | Limit | What counts |
|---|---|---|
| `login_per_ip_and_email` | 5 per minute | Failed logins for one email from one IP. |
| `login_per_ip` | 20 per hour | Failed logins from one IP, any email. |
| `register_per_ip` | 5 per hour | Registrations from one IP. |
| `password_reset_request_per_ip` | 5 per hour | Reset requests from one IP. |
| `password_reset_request_per_email` | 3 per hour | Reset requests for one email, from anywhere (no mailbox flooding). |
| `password_reset_per_ip` | 10 per hour | Reset attempts (token submissions) from one IP. |
| `password_change_per_user` | 5 per 15 minutes | Password change attempts of one user. |

Successful logins don't count. While a login limit is exhausted even the right password gets `429`. Separately, `LOGIN_LOCKOUT_THRESHOLD` (10) failed logins in a row lock the account for `LOGIN_LOCKOUT_DURATION` (15 min): during the lock every login answers the usual `401 INVALID_CREDENTIALS`, so a lock reveals nothing, and a password reset lifts it. A successful login resets the count.

### Vacancies

A user sees only vacancies **visible to them**: those in results of their own search jobs, or in their saved list (architecture §8.2). There is no public catalog. Anything else, including another user's results, is `404 NOT_FOUND`.

| Method | Path | Auth | Success |
|---|---|---|---|
| GET | `/api/v1/vacancies` | session | `200 {items: VacancySummaryOut[], next_cursor: string \| null}` |
| GET | `/api/v1/vacancies/{vacancy_id}` | session | `200 VacancyDetailOut`, or `404` if unknown or not visible |

**Query parameters** (all optional; unknown parameters are rejected with `422`):

| Parameter | Meaning |
|---|---|
| `q` | Text in title or company, 2–100 characters, case-insensitive. |
| `source` | Source key; repeat for several (`?source=a&source=b`). |
| `remote_type`, `employment_type`, `experience_level` | Enum values; repeat for several. |
| `country` | ISO 3166-1 alpha-2 (case-insensitive). |
| `city` | Exact city name, case-insensitive. |
| `salary_min_eur` | Monthly EUR the posting's range must reach. Only postings with a comparable salary match: EUR amounts with a known period until FX rates land (TD-14, M5.11). Other currencies are excluded while this filter is set, not converted by guesswork. |
| `published_within_days` | 1–365. Postings without a publication date are excluded while set. |
| `include_inactive` | `true` includes postings the source reports closed (default `false`). |
| `sort` | `date` (default): newest publication first. `salary`: highest comparable monthly EUR first. Unknown values always sort last. |
| `limit`, `cursor` | Page size 1–100 (default 25), and the `next_cursor` of the previous page. A cursor only continues the sort it came from; a malformed or mismatched cursor is `422` with `details: {"field": "cursor"}`. |

**Duplicates:** the same posting on several sources is one item. The most complete visible record represents the group, and `also_on` lists the other sources with their original URLs (TD-16).

**`VacancySummaryOut`:** `id, title, company, location {country, region, city}, remote_type, employment_type, experience_level, salary, description_snippet, url, source {key, name, attribution_text}, published_at, collected_at, last_verified_at, freshness, also_on[]`.
- `url` is the original posting URL, never rewritten (VACANCY-002).
- `salary` is `{min, max, currency, period}` as published, or `null` when the source gave none: show "Not specified", never an estimate (VACANCY-003).
- `freshness` is `fresh`, `stale` (published over 30 days ago or not re-verified for 7 days, AMB-11) or `removed` (closed at the source). Show a warning for anything but `fresh` (SOURCE-004, VACANCY-004).

**`VacancyDetailOut`** adds `description` (only when the source's storage policy allows full text, TD-23), `requirements`, `responsibilities`, `skills`, `language`, `salary_raw`, `location_raw`, `removed_at`.

### Profile

The signed-in user's professional profile (PROFILE-001..002) and skills. Every route works only on the caller's own data; there is no way to address another user's profile.

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| GET | `/api/v1/profile` | session | none | `200 ProfileOut`. Empty (`updated_at: null`) while it holds no profile data (never saved, or cleared). |
| PATCH | `/api/v1/profile` | session + CSRF | `ProfileUpdate` (any subset of fields) | `200 ProfileOut`. Fields left out stay; `null` clears a nullable field; lists and `salary` are replaced as a whole. |
| DELETE | `/api/v1/profile` | session + CSRF | none | `204`. Clears all profile fields and skills. The account and consent settings stay. Repeating is harmless. |
| GET | `/api/v1/profile/skills` | session | none | `200 {items: UserSkillOut[]}`, sorted by name. |
| PUT | `/api/v1/profile/skills` | session + CSRF | `{skills: [{name, level?, years_experience?}]}` (≤ 100) | `200 {items}`: exactly this list. `[]` removes all. |
| GET | `/api/v1/skills?q=&limit=10` | session | `q` 1–50 chars, `limit` 1–20 | `200 {items: [{id, name}]}`: dictionary skills whose name or alias (EN/RU) starts with `q`, exact matches first. For autocomplete. |

**`ProfileUpdate` / `ProfileOut`:** `display_name` (≤ 100), `desired_roles[]` (≤ 10, 1–100 chars each, duplicates ignored case-insensitively), `location {country (ISO 3166-1 alpha-2), region, city}` (≥ 1 field; output adds `source`, `manual` when typed by the user), `salary` (same shape and rules as the search `salary`: `{min?, max?, currency, period=month}`, min ≤ max, ≥ 0, ISO 4217), `work_formats[]`, `employment_types[]`, `experience_level`, `languages [{code (ISO 639-1), level (A1–C2 or native)}]` (each code once, ≤ 20), `relocation_ready`, `summary` (≤ 5000). Output adds `updated_at`. Unknown fields, including sensitive attributes (age, gender, nationality, religion, health, marital status, photo) and settings (`preferred_locale`, `timezone`, `ai_use_*`, see [Settings](#settings)), are rejected with `422`.

**Skills:** `name` is a dictionary skill or alias in any case (`питон`, `k8s`, `Project Management`); `level` is `beginner | intermediate | advanced | expert`; `years_experience` 0–70 with one decimal. Unknown or repeated skills reject the whole request with `422 VALIDATION_ERROR`, one `details` entry per bad row: `{loc: ["body", "skills", <index>, "name"], type: "unknown_skill" | "duplicate_skill", message}`.

**In searches:** each new search run stores a snapshot of the profile and skills in its context (see `docs/database.md`, `search_jobs.context`), so the next search uses the current profile and later edits never change a running one.

### Settings

The signed-in user's settings and consents (M4.3, PROFILE-003/004, AMB-09). Separate from the profile: `PATCH /profile` can't change them, and `DELETE /profile` keeps them. Only the caller's own settings; a `user_id` (or any other unknown field) in the body is `422`.

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| GET | `/api/v1/settings` | session | none | `200 SettingsOut`. |
| PATCH | `/api/v1/settings` | session + CSRF | `SettingsUpdate` (any subset) | `200 SettingsOut`. Fields left out stay; `null` is `422` (none is nullable); `{}` changes nothing. |
| GET | `/api/v1/settings/personalization` | session | none | `200 PersonalizationOut`: what data is held and where it is used (PROFILE-004). |

**`SettingsOut` / `SettingsUpdate`:** `preferred_locale` (`en` or `ru`) and `timezone` (IANA name): the same values registration sets and `/auth/me` returns, under the same names; `ai_use_profile` (default `true`): the AI assistant may use the profile; `ai_use_history` (default `false`): the AI assistant may use past searches.

**`PersonalizationOut`:** `{ai_use_profile, ai_use_history, items: [{data, has_value, used_for[]}]}` with one item per kind of data: `display_name`, `summary`, `desired_roles`, `skills`, `experience_level`, `languages`, `salary`, `work_formats`, `employment_types`, `relocation_ready`, `location`, `search_history`. `has_value` says whether the app holds it now. `used_for` lists codes the UI translates: `matching` (deterministic match levels, always for the profile data a search snapshots; clearing the profile stops it) and `ai_assistant` (the profile data only with `ai_use_profile`, `search_history` only with `ai_use_history`). Name and summary are stored but never used (`[]`).

### Searches and search runs

| Method | Path | Auth | Success |
|---|---|---|---|
| POST | `/api/v1/searches` | session + CSRF | `201 SearchOut`. Body `{title?, params: SearchParamsV1}`; stored `confirmed` (the UI shows the review step, SEARCH-004/005). |
| GET | `/api/v1/searches/{id}` | session | `200 SearchOut` |
| POST | `/api/v1/searches/{id}/run` | session + CSRF | `202 SearchJobOut` (new run) or `200` (the same run: `Idempotency-Key` replay, or the search already has an active run). |
| GET | `/api/v1/searches/{id}/jobs` | session | `200 {items: SearchJobOut[], next_cursor}`, newest first. |
| GET | `/api/v1/search-jobs/{id}` | session | `200 SearchJobOut` with `ETag`; `304` for a matching `If-None-Match`. Poll every 2–5 s until a terminal status (TD-25). |
| POST | `/api/v1/search-jobs/{id}/cancel` | session + CSRF | `200 SearchJobOut` (`cancelled`; repeating is harmless) or `409 JOB_ALREADY_FINISHED`. |
| GET | `/api/v1/search-jobs/{id}/results` | session | `200 {items: JobResultOut[], next_cursor}`: the run's vacancies with the `/vacancies` query parameters, sorting, cursor and duplicate grouping. |

Another user's search or run is `404` everywhere.

**`SearchParamsV1`** (TD-10): `roles[]` (1–10, required, SEARCH-003), `keywords[]`, `salary {min?, max?, currency, period=month}` (min ≤ max, ≥ 0, ISO currency), `location {country?, region?, city?, radius_km?}` (radius needs a city), `work_formats[]`, `experience_levels[]`, `employment_types[]`, `vacancy_languages[]`, `published_within_days`, plus `skills[]` and `relocation_ready`, which feed matching and are not filters.

**Run lifecycle:** `pending → running → completed | partially_completed | failed`, or `cancelled`. A run gets one row per enabled source; each source runs independently:
- `completed`: every source succeeded (even with 0 results). `partially_completed`: at least one succeeded and at least one failed or timed out. `failed`: none succeeded (`error_code` `ALL_SOURCES_FAILED`, or `NO_SOURCES_RAN` if every source was disabled after creation). One failing source never fails the others.
- Retryable source errors (`SOURCE_UNAVAILABLE`, `SOURCE_TIMEOUT`, `SOURCE_RATE_LIMITED`, `SOURCE_RATE_LIMITER_UNAVAILABLE`) are retried up to `SOURCE_RUN_MAX_ATTEMPTS` while time remains; others (`SOURCE_AUTH_FAILED`, `SOURCE_BAD_RESPONSE`, `SOURCE_NOT_CONFIGURED`, `SOURCE_QUOTA_EXHAUSTED`) are final.
- At the deadline (`SEARCH_JOB_DEADLINE_SECONDS`, default 120 s) the run is finalized with what it has; unfinished sources become `timed_out` / `SOURCE_DEADLINE_EXCEEDED`. This also happens on the next read if the worker died.
- Cancel ends the run at once; sources still in flight finish importing, but their results are not linked (`SOURCE_RUN_CANCELLED`).

**`SearchJobOut`:** `id, search_id, status, progress {sources_total, sources_done, results_so_far}, result_count, error_code, sources[], filter_warnings[], created_at, started_at, finished_at, deadline_at`. Each source: `key, name, status, attempts, fetched_count, stored_count, error_code, filters`.

**Filters a source can't apply are never silently ignored.** For each requested filter, `sources[].filters[filter]` is `{mode, excluded, unverified}`:

| Mode | Meaning |
|---|---|
| `source` | Sent in the source's query; its results are trusted for this filter. |
| `local` | Checked after retrieval on the normalized vacancy. Clear mismatches are excluded (`excluded`); vacancies without the needed data are kept and flagged (`unverified`). |
| `unsupported` | The source never provides the data (e.g. Adzuna: work format, experience level, language, radius). Every result is flagged. |

`filter_warnings[]` summarizes this per filter: `{filter, unsupported_by: [source keys], unverified_results}`, and every result in `/results` lists its `unverified_filters`. The UI must show these instead of presenting such results as matches. Salary filters compare monthly amounts in the same currency; other currencies stay unverified until FX rates (M5.11).

## Internal API (n8n → backend)

`/internal/v1` is how n8n drives search runs when `JOB_DISPATCHER=n8n` (TD-06, TD-09, architecture §8.3). It is not public: the Next.js rewrite forwards only `/api/v1`, the backend publishes no port, and these routes are left out of the OpenAPI document and the generated frontend types.

**Authentication (every route).** `Authorization: Bearer <INTERNAL_API_TOKEN>`, `X-Timestamp: <Unix seconds>` and `X-Signature: sha256=<hex HMAC-SHA256(INTERNAL_HMAC_SECRET, canonical)>`, where `canonical` is four lines joined with `
`: the timestamp, the method in capitals, the path with query, and the SHA-256 hex of the raw body. Timestamps more than `INTERNAL_SIGNATURE_MAX_AGE_SECONDS` (300) from the server clock are refused. Any failure is `401 UNAUTHENTICATED`; so is every request while the token or the secret is not configured.

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/internal/v1/jobs/{id}/context` | none | `200 {job_id, status, deadline_at, sources: [keys]}`. No search parameters or profile: n8n needs no user data. |
| POST | `/internal/v1/jobs/{id}/status` | `{"status": "running"}` | `200 {job_id, status: "running"}`, idempotent. `410 JOB_NOT_RUNNING` if the run is over. |
| POST | `/internal/v1/jobs/{id}/sources/{key}/run` | none | `200 {job_id, source, status, attempts, fetched_count, stored_count, error_code}`: runs the source (adapter → ingest → link, with the backend's own retries of retryable source errors) and returns its recorded outcome. Repeating returns the same outcome without fetching again. `410` if the run is over, `404` for an unknown run or a source not in it. |
| POST | `/internal/v1/jobs/{id}/finalize` | none | `200 {job_id, status, result_count, error_code}`: the terminal status once every source finished or the deadline passed, otherwise still `running`. Idempotent. |
| POST | `/internal/v1/maintenance/sweep-jobs` | none | `200 {finalized: n}`: finishes active runs past their deadline (Cron, every minute). |

**Trigger (backend → n8n).** On `POST /searches/{id}/run` the backend POSTs `{"job_id", "request_id"}` to `N8N_WEBHOOK_URL`, signed the same way with `N8N_WEBHOOK_SECRET` (path = the webhook URL path). One retry; if n8n still can't be reached or answers non-2xx (redirects are not followed), the run fails at once with `error_code: DISPATCH_ERROR` and its sources become `skipped` / `SOURCE_NOT_RUN`, which the `202` response already shows.
