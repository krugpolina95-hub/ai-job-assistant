## TD-01 — Monorepo
**Context.** The SRS §12 defines one repository with `frontend/`, `backend/`, `n8n/`, `docs/`. The frontend and backend must deploy independently (§4.3).
**Decision.** One Git repository with the SRS layout. Each app has its own Dockerfile, dependency manifest, `.env.example` and CI job, filtered by path.
**Alternatives.** Polyrepo: harder to change the API and UI together, and harder to share contract generation.
**Consequences.** One PR can change the API and UI together. Deployment is still per app.

## TD-02 — Stack versions and tooling
**Decision.**
| Area | Choice |
|---|---|
| Python | 3.12, **uv** for dependency and venv management, **ruff** (lint + format), **mypy** (strict on `services/`, `schemas/`) |
| Backend libs | FastAPI, Pydantic v2, pydantic-settings, SQLAlchemy 2.x (async, `asyncpg`), Alembic, httpx, structlog, argon2-cffi (via `pwdlib`), tenacity (retries) |
| Node | 22 LTS, **pnpm**, ESLint, Prettier, TypeScript strict |
| Frontend libs | Next.js (App Router, current stable), React, Tailwind CSS, shadcn/ui, React Hook Form, Zod, TanStack Query, next-intl, openapi-typescript + openapi-fetch |
| Database | PostgreSQL 16 with `pg_trgm`, `citext` |
| Automation | n8n (self-hosted, pinned version), its own Postgres database |
| Cache / limits | Redis 7 (TD-18) |
| Proxy | Caddy 2 |

**Consequences.** Versions are pinned in lockfiles. Upgrades go through Renovate/Dependabot PRs.

## TD-03 — Authentication: opaque server-side sessions
**Context.** AUTH-006 allows cookies or short-lived tokens (CON-12). We need logout, revoking all sessions on password change, and lockouts. SSR pages in Next.js need to know the user.
**Decision.**
- On login, generate 256-bit random token → store `sha256(token)` in `user_sessions` with `expires_at` (idle 7 days, absolute 30 days; "remember me" off = browser-session cookie + 12 h absolute).
- Cookie `sid`: `HttpOnly; Secure; SameSite=Lax; Path=/`.
- **CSRF:** double-submit token. A non-HttpOnly `csrf` cookie plus an `X-CSRF-Token` header is required on POST/PUT/PATCH/DELETE. Together with SameSite=Lax this covers CSRF.
- Password change → delete all sessions and issue one new session to the browser that made the change (a copied cookie stops working too). Password reset → delete all sessions. Logout → delete the current session.
- Sliding expiry is updated at most once every 5 minutes to limit write load.
**Alternatives.** JWT access + refresh tokens: revocation is harder and there's more code. Offers little benefit at MVP scale. Third-party auth (Auth0, Clerk): adds a vendor and cost, and the SRS asks for our own email/password flow.
**Consequences.** Each authenticated request does one indexed DB lookup (optionally cached in Redis for 60 s). Easy to revoke. No token lives in JS.

## TD-04 — Password hashing
**Decision.** Argon2id (`m=19 MiB, t=2, p=1` per current OWASP guidance; tune so hashing takes ~100–250 ms on production hardware). Rehash on login when parameters change. Password rules: 10–128 characters, no forced composition rules, reject the email address itself. An optional check against a local list of common passwords.
**Consequences.** Satisfies AUTH-003. Login has a fixed CPU cost, which also helps against brute force.

## TD-05 — Same-site topology via Next.js rewrite proxy
**Context.** Separate frontend and backend deployments make cross-origin cookies fragile (third-party cookie restrictions, CORS preflights) (RISK-06).
**Decision.** The browser only talks to the frontend origin (`app.example.com`). Next.js `rewrites` forward `/api/v1/*` to the internal FastAPI URL. Server components call FastAPI directly over the internal network and forward the `sid` cookie. FastAPI is not publicly exposed except `/health` for the proxy. The alternative, if the frontend is ever hosted separately (e.g. Vercel): `api.example.com` under the same registrable domain with cookie `Domain=.example.com` and a strict CORS allow-list.
**Alternatives.** Public API with CORS and cross-site cookies: more fragile and a larger attack surface.
**Consequences.** No CORS in the default setup. Next.js is in the request path (acceptable: slight latency). Rate limiting must use the real client IP → trust `X-Forwarded-For` only from the proxy.

## TD-06 — n8n is a thin orchestrator
**Context.** The SRS puts normalization, dedup and matching inside n8n (§5.2, WF-001, WF-004) but also requires business logic in FastAPI and says n8n must not become the only store of logic or data (§4.3, §15) (CON-01, CON-04, CON-05, CON-08, CON-13). The MVP DoD requires the search to run through n8n.
**Decision.**
- The backend owns: job state machine, job context snapshot, source adapters, normalization, dedup, persistence, matching.
- n8n owns: receiving the signed trigger, fan-out to sources (parallel, per-source timeout and retries), merging per-source outcomes, calling finalize, error workflow, **scheduled jobs** (stuck-job sweep, saved-vacancy re-verification, FX refresh, retention cleanup).
- n8n only talks to the backend through `/internal/v1/*` endpoints using a service token + HMAC. It has **no credentials for the app database**.
- WF-003 (AI clarification) and WF-004 (matching) are **not** n8n workflows in the MVP. Matching runs in the backend during finalize (see TD-07, TD-11).
**Alternatives.** (a) The logic in n8n as specified: hard to test, version and review, and duplicates validation. (b) No n8n (Celery/ARQ workers): simpler, but violates the DoD. It stays available through TD-09.
**Consequences.** Workflows are small and stable. Most tests are Python unit tests. n8n outages degrade to the inline dispatcher in dev and can be switched by config in production.

## TD-07 — AI integration from the backend, provider-agnostic
**Context.** AI-006 allows the backend or n8n. The `/api/v1/ai/*` endpoints are synchronous and user-facing (latency matters). AI-007 needs Pydantic validation. §4.3 requires a swappable provider.
**Decision.**
- `app/integrations/ai/` defines `LLMProvider` with `generate_structured(task, messages, schema, model_tier) -> (parsed, usage)`. The first implementation uses the provider chosen in M0. **Default proposal: Anthropic Claude** through the official SDK: a fast, low-cost tier for parse/clarify and a mid tier for explanations. Model IDs live in config, not code, and are confirmed when implementation starts.
- Structured output via tool/JSON-schema mode generated from the Pydantic model → validate → one repair retry with the validation errors → otherwise `AI_INVALID_RESPONSE` and the UI falls back to the form.
- Prompts live as versioned templates in `app/integrations/ai/prompts/{task}.{version}.md`. `prompt_version` is logged.
- Grounding post-checks (AI-004): extracted skills must appear in the user text, profile, or skill aliases. Salary numbers must appear in the text or profile. Anything ungrounded is removed and added to `warnings`.
- Timeouts: 20 s. Retries: 1 on 429/5xx with jitter. A circuit breaker opens after 5 consecutive failures for 60 s.
- Cost controls: input caps, per-user daily quota (default 50 AI calls), cache of parse results keyed by `sha256(locale + normalized text + profile_hash)` for 24 h, `ai_interactions` records tokens and latency.
**Alternatives.** AI through n8n AI nodes: the key is protected, but latency goes up, validation is duplicated and testing is harder.
**Consequences.** One place for AI guardrails. n8n never needs AI credentials in the MVP.

## TD-08 — Source adapters in the backend
**Context.** SOURCE-001 defines a code interface. WF-002 defines per-source n8n logic (CON-02).
**Decision.**
```text
class SourceAdapter(Protocol):
    key: str                                  # get_source_name()
    def rate_limits(self) -> RateLimit        # get_rate_limits()
    def supports(self, params) -> Capability  # which filters the source can honor
    async def search(self, params, ctx) -> list[RawVacancy]
    def normalize(self, raw) -> VacancyIn
    def validate(self, v: VacancyIn) -> ValidationResult
```
- A registry maps `sources.adapter_key` → class. A source works only if its adapter is registered **and** `sources.is_enabled` is true **and** `compliance_reviewed_at` is set.
- Rate limiting uses a Redis token bucket per source. Every outbound request carries an honest `User-Agent` with contact info (SOURCE-003: don't hide identity).
- `MockSourceAdapter` with deterministic fixtures (including missing salary/date, duplicates, HTML) is always available in dev and test.
- n8n WF-002 calls `POST /internal/v1/jobs/{job_id}/sources/{key}/run`. The backend runs the adapter, then normalizes, validates and ingests, and returns counts and status.
**Consequences.** Adding a source = one Python module + fixtures + tests + a seed row. No n8n change is needed.

## TD-09 — `JobDispatcher` abstraction
**Decision.** `JobDispatcher.dispatch(job_id)` has two implementations:
- `N8nDispatcher`: signed POST to the WF-001 webhook (default in staging and production; the DoD requires it).
- `InlineDispatcher`: runs the same orchestration steps in-process as a FastAPI background task (unit tests, local dev without n8n, emergency fallback).
Both call the same internal service functions, so behavior is identical.
**Consequences.** The backend pipeline can be tested without n8n. The SRS dependency on n8n does not become a single point of failure.

## TD-10 — Canonical `SearchParams` schema
**Context.** The form (SEARCH-002) and AI output (AI-005 example) use different field sets.
**Decision.** One Pydantic model `SearchParamsV1`, exported to OpenAPI → TypeScript/Zod:
`roles[] (min 1)`, `keywords[]`, `salary {min, max, currency, period}`, `location {country, region, city, radius_km, source, confidence}`, `work_formats[]`, `experience_levels[]`, `employment_types[]`, `skills[]`, `vacancy_languages[]`, `published_within_days`, `relocation_ready`.
The AI response wraps it: `{params: SearchParamsV1 (partial), missing_information[], questions[], warnings[], explanation, needs_confirmation}`. Enums are shared (`remote|hybrid|onsite`, `intern|junior|middle|senior|lead`, `full_time|part_time|contract|internship|temporary`). `searches.params_schema_version` enables migrations.
**Consequences.** One validator for both entry paths. AI output can't bypass business validation.

## TD-11 — Rule-based matching; LLM only explains
**Context.** MATCH-001..004, AI-004, AI-008. Explanations must be consistent and must not invent facts. A complex ML model is out of scope.
**Decision.**
- The deterministic scorer computes factor scores in 0..1 with weights (initial, versioned as `algorithm_version=1`): title 0.25, skills 0.25, experience 0.15, location/format 0.15, salary 0.10, employment type 0.05, language 0.03, freshness 0.02. Unknown vacancy data → the factor is neutral (0.5) and flagged as "unknown", **not** penalized.
- Levels: High ≥ 0.70, Medium 0.45–0.69, Low < 0.45. Hard mismatches (e.g. onsite in another country and not relocation-ready) cap the level at Low.
- Output: `level`, `factors[] {name, score, status: match|partial|mismatch|unknown, detail}`, `matching_skills`, `missing_skills`, `reasons[]` (template-generated, localized).
- Optional AI polish: for the top 20 results, or on demand when the user opens the detail page, the LLM rewrites the **computed factors** into 2–3 sentences in the user's locale. The prompt receives only the factors and skill lists, never vacancy free text. Output is validated and must not add new facts. Templates are the fallback.
- MATCH-004: only professional fields enter the scorer. There are no sensitive attributes in the schema.
**Consequences.** Matching is cheap, explainable, testable and consistent. AI cost is bounded.

## TD-12 — Idempotency and concurrency
**Decision.**
- `POST /searches/{id}/run` accepts an `Idempotency-Key` header (the UI generates a UUID per click). Unique on `(user_id, idempotency_key)`. A replay returns the existing job.
- If a job for the same search is already `pending/running`, return it (HTTP 200 + existing `job_id`) instead of creating a new one.
- Maximum 2 active jobs per user → otherwise `409 JOB_LIMIT_REACHED`. Maximum 20 runs per hour → `429`.
- n8n calls carry `request_id` + `job_id`. Ingest upserts on vacancy dedup keys. `search_job_results` is unique on `(job_id, vacancy_id)`. `vacancy_matches` is unique on `(search_job_id, vacancy_id)`. Status transitions are validated (e.g. `completed → running` is rejected, and repeated transitions are no-ops).
- Cancellation: `cancel_requested_at` is set. The backend immediately moves the job to `cancelled`. Later ingest calls for this job return `410 JOB_CANCELLED`, and n8n stops.
**Consequences.** Satisfies SEARCH acceptance "no uncontrolled number of jobs", §4.2 and §8.5.

## TD-13 — Server-side results, filtering and sorting
**Decision.** Results are stored per job (`search_job_results`), capped at 200. `GET /api/v1/search-jobs/{id}/results?level=&remote=&salary_min=&source=&sort=match|date|salary&cursor=&limit=25`. Sorting by match uses the internal score (never shown). Cursor pagination.
**Alternatives.** Client-only filtering: simpler, but breaks at larger sizes and duplicates logic.
**Consequences.** MATCH-005 is satisfied. Filter logic is tested once, in the backend.

## TD-14 — Salary normalization
**Decision.** Store `salary_min/max`, `salary_currency` (ISO 4217), `salary_period` (`hour|day|month|year|unknown`), plus `salary_raw` text. For filtering and matching only, compute `salary_monthly_min/max_eur` using a daily ECB reference-rate table (`fx_rates`, refreshed by an n8n Cron job) and standard conversions (hour×168, day×21.7, year/12). Unknown period → excluded from salary filtering and the salary factor is `unknown`. The UI always shows the original values. Converted values carry a "≈" marker and appear only in the user's currency preference context.
**Consequences.** VACANCY-003 is respected: nothing is invented. Comparisons across currencies are approximate and labelled as such.

## TD-15 — Location
**Decision.** IP → a local GeoIP database (MaxMind GeoLite2-City or DB-IP Lite, license and attribution to be confirmed in M0). It's loaded into memory and updated monthly. Returns country/region/city + an accuracy radius → confidence `high|medium|low`. The client IP comes from the trusted proxy header. **IPs are not stored.** Only the resolved city/country is stored, and only when the user saves it. Browser geolocation (opt-in) → the client sends lat/lon once → the server reverse-geocodes against an offline cities dataset (GeoNames `cities15000`) → only the city is kept (LOCATION-004). Priority order per CON-10.
**Consequences.** No personal data goes to third parties. Works offline. Accuracy limits are shown to the user (LOCATION-005).

## TD-16 — Deduplication
**Decision.** On ingest, check in order:
1. `(source_id, external_id)` → same record (update, refresh `last_verified_at`).
2. `canonical_url` (lowercased host, tracking params stripped, trailing slash normalized) → same record within a source; across sources → same `duplicate_group_id`. Records are never merged across sources, because each keeps its own source's storage policy and attribution (AMB-10).
3. `content_hash` (fields per AMB-24) → same record within a source; across sources → same `duplicate_group_id`.
4. Fuzzy: `normalized_title` trigram similarity ≥ 0.85 **and** same normalized company **and** same city/remote type, within 30 days → same `duplicate_group_id` (grouping only, never merging).
Results are shown one card per group, with the most complete record as primary and "Also on: …". The primary is chosen among the records the user can see.
**Consequences.** Satisfies VACANCY-001 without destroying data. False positives only affect grouping.

## TD-17 — Deployment and CI
**Decision.**
- **Local:** `docker compose up` → postgres, redis, backend, frontend, n8n (+ n8n-db), mailpit, caddy. Seed and migrate commands are in the README.
- **CI (GitHub Actions) from M0:** backend (ruff, mypy, pytest with a Postgres service), frontend (lint, typecheck, vitest, build), OpenAPI drift check, n8n workflow JSON lint (no credentials embedded), Docker build. Playwright E2E on main and nightly.
- **MVP production:** a single VM (region chosen after the legal review) with Docker Compose + Caddy (auto-HTTPS, HSTS). Postgres is managed if the budget allows, otherwise a container with daily `pg_dump` to offsite object storage + WAL archiving later. Staging mirrors production. Deploys use a tagged images pipeline (build → push to registry → `compose pull && up -d` → run migrations → smoke test).
- Secrets: an `.env` on the server (root-only, 0600) or the provider's secret manager. `.env.example` files are committed with placeholders.
**Alternatives.** Kubernetes: premature. PaaS (Render/Fly/Railway): viable, and good if the team prefers it. n8n hosting fits less well there.
**Consequences.** Low cost and simple operations. RISK-16 is accepted for the MVP.

## TD-18 — Redis
**Context.** The SRS stack has no cache, but rate limiting (AUTH-006, source rate limits) must work across processes.
**Decision.** Add Redis for rate-limit counters (sliding window), source token buckets, the AI parse cache, and an optional session cache. No business data in Redis. Losing it is harmless.
**Alternatives.** Postgres-based counters: fewer services, more DB load and more code. Acceptable fallback.

## TD-19 — API contract
**Decision.** FastAPI generates OpenAPI 3.1. CI exports `openapi.json` and the frontend generates types (`openapi-typescript`). Form-level Zod schemas mirror the backend constraints, and shared enums come from the generated types. Error envelope: `{"error": {"code", "message", "details", "request_id"}}`. Error codes come from a catalog (`backend/app/core/errors.py`, documented in `docs/api.md`). Cross-user access returns **404** (not 403) to avoid leaking whether a resource exists.
**Consequences.** Contract drift fails CI. The SRS error format is satisfied.

## TD-20 — Internationalization
**Decision.** Frontend: `next-intl`, locale-prefixed routes (`/en/...`, `/ru/...`), message catalogs in `frontend/messages/{locale}.json`, ICU plural rules, `Intl` formatting for dates, numbers and currency, and the user's time zone. Backend: returns **error codes** plus parameters. The frontend translates. Transactional emails are localized templates on the backend. AI replies use `locale` passed explicitly. Adding a language = a new catalog + email templates + a prompt locale note.
**Consequences.** Satisfies §1.5 and §4.5.

## TD-21 — Observability
**Decision.** structlog JSON logs with `request_id` (generated at the proxy or backend and returned in `X-Request-ID`), `user_id` (hashed in logs), `job_id`. The `request_id` is propagated to n8n and back. Sentry (or GlitchTip, self-hosted) for backend and frontend exceptions, with PII scrubbing. Metrics: Prometheus endpoint on the backend (request latency, job durations, per-source success rate, AI latency/tokens) → Grafana later. MVP alerting: uptime check + Sentry alerts + a daily AI cost report. Centralized logs: Docker logs → Loki (or the provider's log service) in the hardening milestone.
**Consequences.** SRS §5.1 centralized logging and §4.2 logging of important operations.

## TD-23 — Per-source storage policy
**Context.** CON-06: storing `description` vs not copying full texts without a legal basis.
**Decision.** `sources.storage_policy ∈ {full, snippet, none}` + `retention_days`, set during the compliance review. `snippet` keeps ≤ 500 characters plus the structured fields. `none` keeps structured fields only. The detail page renders what is allowed and always shows "View original" as the primary CTA. HTML is converted to sanitized plain text/markdown on ingest.
**Consequences.** Compliance is per source and changes through configuration.

## TD-24 — Deletion and retention
**Decision.** Account deletion = transactional hard delete of the user and all user-owned rows (FK `ON DELETE CASCADE`), and sessions revoked. An `audit_log` entry is kept with `sha256(user_id + pepper)` and no email. History deletion is scoped per AMB-13. Retention is enforced by daily jobs: AI debug content 7 days, `ai_interactions`/`auth_events` 180 days, orphaned vacancies (not saved, not in a job from the last 90 days) 90 days or less if the source policy requires it.
**Consequences.** Satisfies §7.12 and §10 privacy rights. Backups age out according to the backup retention (30 days), which is documented in the privacy policy.

## TD-25 — Polling for job progress
**Decision.** `GET /search-jobs/{id}` returns `status`, `progress {sources_total, sources_done, results_so_far}`, `updated_at`. TanStack Query polls every 2 s and backs off to 5 s after 30 s. It stops on a terminal status. It supports `ETag`.
**Alternatives.** SSE/WebSockets: better UX, more infrastructure (proxy timeouts, auth on streams). Revisit after the MVP.

## TD-26 — Identifiers
**Decision.** UUID primary keys everywhere (per the SRS). App-generated UUIDv7 gives index locality and time ordering. External IDs are stored as text. Public API exposes UUIDs only.

## TD-27 — Email
**Decision.** `EmailSender` interface. SMTP implementation. Provider chosen in M0 (e.g. Postmark, SES, Resend, Mailgun). SPF/DKIM/DMARC on the sender domain. Dev uses **Mailpit** in compose. Templates are localized (EN/RU) and plain-text first. Used for password reset and email verification.
